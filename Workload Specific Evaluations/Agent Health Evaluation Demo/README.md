# Agent Health Evaluation Demo

## 1. What Is This

This is a demo of an end-to-end **agent health evaluation** workflow: given an existing deployed agent, how do you figure out whether it's healthy, without hand-authoring a requirements doc and a metrics suite from scratch?

The workflow has five phases:

1. **Derive a contract** from the agent's own system prompt (and tools, if any) — its stated role, responsibilities, and constraints — via `contract_deriver.py`.
2. **Propose health metrics** from that contract using an LLM, each with a name, definition, scoring rubric, and a traceability reference back to the contract statement that motivated it — via `metric_proposer.py`.
3. **Review real interaction data** in a Streamlit UI (`review_app.py`), where a domain expert reads the agent's actual responses and records an Expected State Label (what the agent should have done/known) and Task Success Feedback (did it actually succeed, pass/fail + rationale).
4. **Score the data** against the proposed metrics using a live AgentCore evaluator — via `evaluator_runner.py`.
5. **Publish the results** to CloudWatch as custom metrics, and surface them — plus any disagreements between the domain expert's feedback and the automated scores — back in the review UI for manual inspection.

The three agents being evaluated (`market_trends`, `customer_insights`, `strategy_synth`) are the existing peer-to-peer restaurant-industry research agents defined in the sibling module.

## 2. Relationship to the Sibling Module

This demo reads from `Workload Specific Evaluations/Multiagent Shared Context Evaluation/` — its `model_config.py` (`PEER_CONFIGS`, `AGENT_MODEL_ID`) and its `review/review_cases.jsonl` review data — but it is **strictly read-only** against that module. Nothing in this package ever creates, modifies, or deletes a file under the sibling module's directory or its spec directory (`.kiro/specs/multi-agent-shared-context-evaluations/`).

Every artifact this demo produces (contracts, candidate metrics, feedback, evaluation results, run summaries) is written under this package's own `output/` directory. `output/` is not checked in (see `.gitignore`); it is regenerated by running the phases below. `persistence.py` is the enforcement point for this: every write call is routed through `resolve_output_path`, which raises if the resolved path would escape `output/` — including an attempt to reach into the sibling module via `..` traversal or an absolute path.

## 3. Prerequisites

- Python 3.10+
- Install dependencies: `pip install -r requirements.txt`
- AWS credentials with access to, in your target region:
  - Bedrock Runtime `InvokeModel` (contract derivation's LLM extraction step and metric proposal)
  - Bedrock AgentCore evaluation capability (Phase 3 scoring)
  - CloudWatch `PutMetricData` (Phase 4 publishing)
- Region comes from `AWS_REGION` (default `us-west-2`), same convention as the sibling module.
- Phases 2–4 read review data from the sibling module's `review/review_cases.jsonl`. That directory is excluded by the repository's top-level `.gitignore`, so a fresh clone falls back to the bundled 3-record sample in `sample_data/` (see "Running from a fresh clone" below).

**This demo's evaluator and dashboard calls are live AWS calls with no mock fallback.** `evaluator_runner.py`'s `agentcore_scorer` and `dashboard_publisher.py`'s `publish_aggregates` both construct their AWS clients outside of any per-item try/except, so a missing-credentials or misconfigured-region failure surfaces immediately as a configuration error rather than being silently swallowed or routed to a simulated path. Running Phase 3 or Phase 4 for real will make real calls against whatever account your ambient credentials resolve to — be sure that's the account/region you intend.

## 4. Running Each Phase

### Running from a fresh clone

`output/` is not checked in, so run the phases in order: Phase 1 first (`python contract_deriver.py`, then `python metric_proposer.py`), which creates `output/contracts/` and `output/metrics/candidate_metrics.jsonl`; then Phase 2 (`review_app.py`) and Phases 3–4 (`run_pipeline.py`). Note `metric_proposer.py`'s `__main__` proposes metrics for `market_trends` only, which matches `run_pipeline.py`'s default `--agent`.

The sibling's `review/review_cases.jsonl` is gitignored, so on a fresh clone `persistence.load_review_records()` uses `sample_data/review_cases.jsonl` instead and prints a one-line notice. That file holds the first 3 rows of a real capture (`live-brief-01-fastcasual`, `live-brief-02-fastcasual-expansion`, `live-brief-03-evfleet`), copied verbatim. When the sibling file exists it is always the primary source. Set `AGENT_HEALTH_USE_SAMPLE_DATA=1` to force the sample anyway.

To regenerate the full 10-record dataset, run the sibling module's `capture_for_review.py` (live Bedrock calls) from `Workload Specific Evaluations/Multiagent Shared Context Evaluation/`; it writes `review/review_cases.jsonl`, which this demo then picks up automatically.

### Phase 1 — Derive contracts and propose metrics

```bash
python contract_deriver.py
```

Derives an `AgentContract` for each of the three peer agents (reading `PEER_CONFIGS` read-only from the sibling module) and persists each to `output/contracts/<agent_name>.json`. Contract extraction tries a Bedrock call first; if that fails for any reason (throttling, missing credentials, malformed response), it falls back automatically to a deterministic heuristic sentence-splitter, so a contract is always produced.

```bash
python metric_proposer.py
```

Runs the validation/filtering sanity checks first (no AWS call), then makes a real Bedrock call proposing candidate metrics for the already-persisted `market_trends` contract, and persists accepted metrics to `output/metrics/candidate_metrics.jsonl` (rejected proposals, with their missing fields, go to `output/metrics/candidate_metrics.rejected.jsonl`). To propose metrics for a different agent, either edit the hardcoded `"market_trends.json"` path in the script's `__main__` block, or call `propose_metrics(contract)` directly from a Python shell/script after loading that agent's persisted contract with `persistence.read_json` + `AgentContract.from_dict`.

You can hand-edit `output/metrics/candidate_metrics.jsonl` before later phases run — `metric_proposer.load_metrics(path)` loads whatever is on disk, LLM-proposed or hand-edited, without distinction.

### Phase 2 / Phase 5 — Review UI

```bash
streamlit run review_app.py
```

Loads review records read-only from the sibling module's `review/review_cases.jsonl` (or the bundled `sample_data/` copy on a fresh clone). For the selected record (navigable via a sidebar selector), the UI shows:

- The brief/task text, one expander per agent's response, and the expected-behavior tag.
- An **Expected State Label** text area (pre-filled with the latest saved label for that record, if one exists) with a Submit button that appends to the Feedback Store.
- A **Task Success Feedback** pass/fail radio plus rationale text area, with a Submit button that appends to the Feedback Store.
- An **Evaluator Run Results** panel: once `output/results/metric_results.jsonl` exists (produced by Phase 3), this shows each metric's average score for the selected record, plus a warning listing any disagreements between domain-expert feedback and the metric scores for that record (found via `feedback_store.find_disagreements`). Before any evaluator run has happened, it shows a plain "no results yet" message.

### Phases 3 + 4 in one command — `run_pipeline.py`
```bash
python run_pipeline.py --records 3 --metrics 4 --agent market_trends
```
Scores the first `--records` review records against the first `--metrics` candidate metrics for `--agent` (loaded from `output/metrics/candidate_metrics.jsonl`, or `--metrics-file`), publishes the per-metric means to CloudWatch, prints a summary table (record, metric, score, short rationale) plus the aggregates and publish report, and saves the full summary, including every rationale verbatim, to `output/runs/<timestamp>_summary.md`. Add `--skip-publish` to score without calling CloudWatch. With the defaults this makes 12 AgentCore evaluate calls and 4 `PutMetricData` calls.

The AgentCore client is constructed before any scoring, so a missing package, credentials, or region aborts the run up front. The exit code is non-zero if any pair or publish failed.

Review records are multi-agent (one response per peer agent, `agent_name == "multi"`). `agentcore_scorer` scores `responses[record.agent_name]` and otherwise falls back to the first response in the record, so `run_pipeline.py` hands it a per-agent view of each record (`agent_name` set to `--agent`). That way the scored text is always `--agent`'s own response, matching the metrics being applied. Records without a response for `--agent` are skipped and listed in the summary.

### Phase 3 — Run the evaluator (library use)

`evaluator_runner.run_evaluation` is a library function, not a CLI script. Call it directly, e.g.:

```python
from metric_proposer import load_metrics
from persistence import load_review_records
from evaluator_runner import run_evaluation

metrics = load_metrics("output/metrics/candidate_metrics.jsonl")
records = load_review_records()  # read-only from the sibling module

results, failures = run_evaluation(metrics, records)
# results/failures are also persisted automatically to
# output/results/metric_results.jsonl and
# output/results/metric_results.failures.jsonl
```

By default `run_evaluation` scores every `(record, metric)` pair using the live `agentcore_scorer`. Each pair is independently wrapped in a try/except, so one failing pair doesn't abort the rest of the run — it's recorded as a `MetricFailure` instead. You can pass a different `scorer` callable (same `(record, metric, reference_label) -> (score, rationale)` contract) for testing without AWS.

### Phase 4 — Publish to CloudWatch (library use)

`dashboard_publisher.publish_aggregates` is also a library function. Call it directly, e.g.:

```python
from persistence import read_jsonl, resolve_output_path
from models import MetricResult
from dashboard_publisher import publish_aggregates

rows = read_jsonl(resolve_output_path("results", "metric_results.jsonl"))
results = [MetricResult.from_dict(row) for row in rows]

report = publish_aggregates(results, agent_name="market_trends")
print(report.published, report.failures)
```

This aggregates scores per metric name and publishes one CloudWatch `PutMetricData` call per metric to the `AgentHealthDemo` namespace, each labeled with `AgentName` and `MetricName` dimensions. A failure publishing one metric doesn't block the others — it's recorded in `report.failures` by metric name.

## 5. Testing

```bash
pytest tests/
```

Runs the default suite: unit and property-based tests (via `hypothesis`) covering contract derivation's fallback path, metric validation/filtering, Feedback Store round trips and lookups, evaluator orchestration and failure isolation (with a fake scorer), and dashboard aggregation/labeling/failure isolation (with a stubbed CloudWatch client). None of these make live AWS calls.

`tests/conftest.py` redirects every persisted-data path (`feedback_store.FEEDBACK_STORE_PATH`, `evaluator_runner.METRIC_RESULTS_PATH`/`METRIC_FAILURES_PATH`, `metric_proposer.CANDIDATE_METRICS_PATH`/`REJECTED_METRICS_PATH`, `run_pipeline.RUNS_DIR`) to a per-test scratch directory under `output/_test_scratch/` and deletes it afterward, so neither the default suite nor the live tests write to the real `output/` data files.

```bash
LIVE_AWS_TESTS=1 pytest tests/test_integration_live.py
```

Runs the live integration tests, skipped by default: one real `agentcore_scorer` call against AgentCore evaluation, and one real `publish_aggregates` call against CloudWatch. It also makes one real Bedrock `propose_metrics` call (its output goes to the test scratch directory) and launches the Streamlit app locally. Requires AWS credentials with the relevant permissions in your target region.

## 6. Known Limitations

- **`agentcore_scorer` is an adapter, not a direct rubric evaluation.** AgentCore's evaluation API is session/span-oriented (it expects real OpenTelemetry traces) and its built-in evaluators take a fixed evaluator ID, not an arbitrary inline rubric. Since this demo's review records are plain brief/response text with no captured trace, `agentcore_scorer` builds a synthetic single-span trace and scores it with the built-in `Builtin.Correctness` evaluator, folding the candidate metric's rubric/definition text into that evaluator's `expectedResponse` field as supplementary context rather than evaluating it directly. The resulting score reflects the built-in evaluator's own correctness judgment of the response in isolation, not a genuine scoring of the proposed rubric. See `agentcore_scorer`'s docstring in `evaluator_runner.py` for the full detail, including why a cleaner path (a custom code-based evaluator per metric) was ruled out as out-of-scope infrastructure provisioning.
- **`run_pipeline.py` is the only end-to-end CLI for Phases 3 and 4.** `evaluator_runner.py`'s and `dashboard_publisher.py`'s own `__main__` blocks run fake-scorer/stubbed-client sanity checks rather than a real run.
- **Scores are coarse and can contradict their rationale.** In the sample run every score came back as 0.0 or 1.0 rather than a graded rubric value. `Builtin.Correctness` judges the response against the expected-response text, which here is the metric's rubric. The judge sometimes reasons about the mismatch between "a rubric" and "a market analysis" instead of applying the rubric, so an individual score can contradict its own explanation (for example, a response the judge says has "exactly 2 sections" scoring 0.0 on a 2–3 paragraph conciseness metric). Read the rationales, not just the numbers.
